# Courier peer-task handoff extension

**Status:** Independently reviewed design proposal, 2026-10-09. The same-team assignment requirement is accepted product intent. Implementation details below remain proposals with named validation gates; this is not implementation readiness, merge approval, rollout approval, or authority to execute on another agent.

## Recommendation and verified baseline

Add direct, structured task handoffs to an **existing named peer** in a pinned team: offer, accept/decline, execution status, result and cancellation. A crew is still an address book, not a scheduler or an authority hierarchy. The feature works with an already-running independent peer and does not require spawning a child agent. Deliver each handoff through one ordinary authenticated E2E DM relationship, retaining SuiteV1 and the existing relay. Do not turn team fanout into competitive task claiming.

There are two different baselines:

- PR162 documentation at `26f89b23` describes address resolution and text fanout, and explicitly keeps shared notes/tasks separate. Its Packet B specifies roster, invitation, acceptance, tombstone and owner-transition types only. The prior team proposal contains no task-execution lifecycle.
- Historical `internal/client/state.go` at `26f89b23` contains structured pairwise task-add/assign/done/reopen; `cmd/courier/state.go` exposes them. This is historical evidence, **not the implementation target**.
- Consolidation PR150 intentionally removes that entire runtime and CLI. At Packet A PR163 `db0f83c68277cb45990193c2dd0e213e44655907`, `state.go` is absent and PROTOCOL §13/§27 reserves retired `cs:1,t:state` payloads of **any version** for silent consumption. Do not revive those files, discriminator, state-sync consumer or task fold. This proposal is a narrowly scoped new handoff protocol, not restoration of the retired shared project-management subsystem.
- PR154's head fetched during this review is `5a617cf53a250288441c0d5696e1fc86c2cec66b`; it differs from the supplied prior `6fea5f63592b9cf27ddc74e36727ae74e7561b70`. The integrator must reconcile moving stack bases before implementation.

## First-release boundary

One immutable offer, one assigner, one existing assignee, one execution attempt. No broadcast assignment, bidding, automatic reassignment, retries of execution, nested delegation, workflow DAG, shared notes, task board, automatic tool access or multi-device distributed scheduler. A new attempt or changed instructions requires a new task ID and fresh policy evaluation. Optional `supersedes_task_id` is provenance only and cannot cancel or restart the old task.

Courier owns authenticated transport, strict handoff types, durable deduplicated offer/event delivery, a context-bound local ledger, observable peer-reported status, and a fenced local claim API. The receiving executor owns admission policy, human approval, work scheduling, sandbox/tools, resource budgets, side-effect idempotency, actual execution, cancellation and the truthfulness of results. Courier never interprets task text as a command to execute and never claims exactly-once effects.

The relay sees ordinary routing/timing/size metadata, never task plaintext, title, status, result or approval evidence. No new relay task database or endpoint is required. Avoid plaintext dashboard push or logs by default; expose local CLI/JSON summaries only. Sending a result or status is still a communication governed by recipient policy.

## Direct addressing and policy

Proposed surface: `courier task offer muse@crew --title ... --body-file ... --accept-before ... --deadline ...`; `task list/show`; and `task accept/decline/status/result/cancel`. Exact CLI spelling remains a decision gate. The execution integration uses typed local APIs, including `claim`, rather than parsing CLI display output.

Resolve `muse@crew` through the reviewed pinned alias and fresh signed roster. Require sender and recipient membership in that same verified snapshot for the team-specific offer. Freeze the full addresses, team ID, roster version/hash, member consent bindings, relay origin and content hash before policy evaluation. Recheck freshness and known membership changes immediately before submission and before recipient acceptance. Handle names never become authorization keys. Do not add an assignee to contacts or a group automatically.

Sender contact/first-contact checks, FS-required policy and per-recipient VHL rules remain mandatory. A task is application content with ordinary-send protections, not privileged machine control traffic that bypasses those gates. If existing send/FS/VHL plumbing cannot safely carry the typed payload, fail closed until its narrow adapter is reviewed. In particular, historical protocol-DM legacy sealing is not permission to bypass a peer's FS-required task policy.

Receipt, a team signature, an offerer's assertion of approval, and transport VHL are not recipient execution authorization. Recipient runtime must separately evaluate authenticated sender, exact immutable offer hash, requested action scope, data destinations, budgets and current local approval. Approvals are local, recipient-specific, revocable and bound to the offer and context. Do not transmit reusable authorization tokens or credentials in the task. The sender can request capabilities; only the recipient's existing policy can permit their use. An unknown or held sender produces a pending request, never a task claim or automatic reply.

Known removal/rebinding or expired roster blocks new offers and acceptance. After acceptance, membership is provenance, not an ongoing execution capability: local policy revocation/removal pauses new work pending re-evaluation. Do not block authenticated stop requests or bounded reconciliation to the original peer merely because the roster has expired. Normal communication/disclosure policy still governs result transmission. This avoids stranding cancellation while granting no new authority.

## New wire namespace and identity binding

Use a **new discriminator and schema**, provisionally `courier.peer-task.v1` (final encoding registered in PROTOCOL before code). Never `cs:1` or any retired channel/state discriminator. Keep the outer SuiteV1 DM envelope, relay API, existing omitted-suite behavior and roster schemas unchanged. Before sending task content, require positive authenticated support for the exact peer-task protocol version from the resolved principal: a fresh verified signed directory capability, provisionally `peer-task-v1`, bound to that principal and selected relay, with an explicit validity bound. If the existing directory proof cannot establish the required freshness/binding, the adapter must block until a separately reviewed support-proof mechanism exists. Missing, stale, withdrawn or incompatible support fails closed; there is no fallback to ordinary chat. Capability support describes decoding only, never admission, available capacity or liveness. Conforming clients recognize the reserved peer-task namespace before generic chat decoding, including when execution is disabled; unknown versions/malformed recognized frames go to bounded local quarantine or a diagnostic rejection, never chat, dashboard plaintext or execution.

These are **conforming-client guarantees**. Existing older clients render unknown payloads as raw chat and may push them as plaintext to their dashboard. This extension cannot retrofit their dispatch behavior; the authenticated sender-side compatibility gate is mandatory. A stale/malicious support advertisement or software downgrade remains a recipient behavior risk, so support freshness/withdrawal and upgrade-before-advertising tests are release gates. Do not infer compatibility from shared team membership, a friendly label or unsigned directory metadata.

The immutable offer uses an acyclic two-level representation. `offer_core` contains schema/domain, relay origin, task ID, both party addresses, complete task content, deadlines and team provenance, but **no** offer hash, signature, event-chain fields or transport envelope ID. Define `offer_hash = SHA256("courier.peer-task.offer.v1\0" || JCS(offer_core))`. The signed offer event carries `offer_core` and that recomputed hash; later events carry the same hash without repeating the core. The event signature covers every canonical event field except its signature, including the core when present. Event hashes likewise exclude signatures but include offer_hash and predecessor references. Verify the computed core hash before applying an offer. This separates immutable task identity from transport-specific approvals without a self-referential hash.

Common signed event payload:

- schema, kind, relay_origin, task_id (256-bit random ID), offer_hash
- assigner_address, assignee_address, actor_address, audience_address
- actor_seq (canonical decimal uint64), previous_actor_event_hash
- issued_at; event-specific causal references
- event-specific body, with explicit bounded strings/arrays

The offer core includes immutable title/instructions, requested output, accept_before, execution_deadline, and team provenance `(team_id, roster_version, roster_hash, assigner_member_binding, assignee_member_binding)`. Requirements are descriptive, never bearer capabilities. Result payload permits bounded text and explicit artifact references/hashes; links do not grant permission to fetch or share and convey no access guarantee.

Apply the already-reviewed strict canonicalization pattern from Packet B through a narrow reusable interface: reject duplicate/unknown fields, invalid encodings, bad address/suite combinations and overlimits; domain-separate signatures and hashes for this schema. Sign canonical bytes without signature fields. Authenticated outer DM sender/recipient must match inner actor/audience; both must be exactly the immutable task parties. All later events bind the entire offer via offer_hash. Wrong context/origin, team, offer hash, actor role or recipient is rejected. Local context IDs are not sent as globally meaningful IDs.

Each participant has its own hash-chained monotonic event stream per task. Buffer missing predecessors within explicit limits; the deny-only early-stop exception below can inhibit execution while a valid cancellation is awaiting its predecessor, but cannot authorize any positive transition; never order execution decisions by sender wall-clock timestamps. Repeated event identity with identical canonical bytes is idempotent; same identity with different bytes freezes the task as equivocation. Explicit references connect response to offer, result to accepted offer/claim attempt, and cancellation outcome to cancellation request. A pair of asynchronous streams does not create global consensus.

## Lifecycle and races

The assignee serializes admission and execution transitions in its local durable ledger; its signed status stream is authoritative evidence of what it reports doing. The assigner has a separate cancellation-request stream. UI always distinguishes local intent, delivery state and last observed recipient state.

An offer is a **proposed assignment**, not an accepted assignment. Local incoming states distinguish `pending_policy` / `awaiting_human` from accepted work; neither state is executable or emits a remote status without communication authorization. Acceptance acknowledges admission of that exact proposed assignment, not availability now, a scheduled start, ongoing liveness, or guaranteed completion. `accepted_waiting` is explicit until a claim and running report establish more. A recipient may decline for capacity or unsupported capability. A lack of response is unknown, never implied acceptance.

1. Offer preparation commits immutable payload and outbox before submission. Relay acceptance is `submitted`, not `accepted` or `running`. Unknown send outcome stays unknown; retry only the same prepared event/envelope under verified dedup guarantees.
2. An unexpired offer may be accepted or declined only by its exact assignee, after local authorization. Acceptance records the exact offer hash. It does not start work. An explicit acceptance policy may authorize bounded status/result replies to the assigner; otherwise obtain the needed communication authorization locally.
3. A local executor atomically claims an accepted task with a random claim token, monotonically increasing fence and bounded lease. Store the lease and execution-intent record durably **before** releasing work. A concurrent claimant loses. The token stays local; remote status reports carry only an attempt ID and fence, which confer no authority.
4. The executor reports running, blocked (with a bounded reason), or terminal succeeded/failed/cancelled. Only the matching local claim/fence may publish execution status/result. Assignee-ledger **admission/control resolutions** before a claim, such as decline, offer expiry, or cancel-before-claim, are separately typed and signed without an executor claim; they cannot assert that work ran or report an execution result. A pending-policy or awaiting-human local state needs no fabricated claim. Post-start stopping/result reports remain claim-bound, except a recovery-required ledger observation that explicitly does not claim executor quiescence. A completed result is peer-reported evidence, not independent verification of external effects. The assigner cannot mark the recipient's execution succeeded.
5. Lease expiry yields `stalled/needs_reconciliation`, not permission to start another attempt. A crashed/paused executor might still have effected work. Reconcile the original executor/side-effect journal before any manual resume; a fresh lease cannot prove the old executor stopped. The first release has no automatic takeover. A local claim is valid only within a shared locked state store; independently copied identities/devices are unsupported and must not advertise a cross-device single-claim guarantee.
6. `accept_before` expiry prevents new acceptance; it never erases the record. Missing acceptance at the assigner means `acceptance_unknown/overdue`, because an earlier valid acceptance might be delayed. Only recipient evidence resolves that uncertainty. Execution deadline is a recipient stop boundary, not a disappearing-message TTL or proof the executor stopped. At the deadline, block new effects and request stop; if stopping is unconfirmed, report `deadline_exceeded/stopping_unknown`, not successful cancellation.
7. Cancellation is an authenticated request from the assigner. The assignee records it before starting if already observed; pending work becomes cancelled. Running work gets a cooperative stop request, and `cancelled` is reported only when execution is quiescent or known not started. If result wins the local race, report `already_terminal` with its result reference. If cancellation wins, late completion cannot rewrite cancelled history; keep any reported effects in the audit trail. Both sides converge using the assignee's ordered resolution, not local arrival order or timestamps. A cancellation received before its offer or an actor-chain predecessor first passes strict shape, inner signature, outer authenticated sender/recipient and context checks. If the cancellation claims that authenticated sender as assigner and this local principal as assignee, persist a **deny-only pending stop marker** keyed by `(context, assigner, assignee, task_id, offer_hash)` immediately, even if its actor sequence is 2 and the offer at sequence 1 is missing. This marker blocks admission and claims for only that exact tuple; it is not a validated lifecycle transition and cannot create a task, prove team membership, confer authority, erase a result or trigger execution. Retain the signed cancellation in bounded predecessor quarantine. When the offer/chain arrives, validate the immutable participants, hash and full causality and convert a valid stop into recipient cancellation resolution. Invalid/incomplete history never unlocks execution automatically: mark security/reconciliation required; explicit local reconciliation is required to clear a pending stop. At quota exhaustion, refuse new admission until safe reconciliation rather than evicting stop markers that could permit delayed work. Unknown senders cannot affect another assigner’s tuple. Do not send automatic stop acknowledgments before normal communication policy allows them.
8. Terminal states do not reopen. The sender may propose another task only after considering unresolved execution/cancellation risk; a new ID is not evidence that duplicate effects are safe.

Clock policy uses a durable observed-time floor and documented skew allowance. Material rollback blocks admission and new effects. Lease liveness uses monotonic time within a process; after restart persisted claims require reconciliation rather than trusting renewed wall-clock duration. No absolute-time policy can defeat a compromised endpoint clock; disclose that limitation.

## Durable delivery, replay and recovery

Maintain context-bound ledger/outbox/claims with Packet A locks, atomic replacement and fsync. Inbound commit/dedup must occur before consumer cursor advancement or exposing a runnable offer. Inbox and dashboard polling must not independently launch work. Admission notifications are replayable, non-authoritative wake hints; they may be duplicated or lost. On startup/restart and bounded periodic reconciliation, the runtime enumerates durable pending offers and accepted-but-unclaimed work and re-evaluates current admission policy. A crash after ledger commit but before notification therefore cannot strand the offer. All notification/poll paths converge on the same atomic admission/claim ledger; no notification directly starts work. At-most-one local active claim is the safety property, not at-most-one notification. Pending human approvals remain pending across restart and cannot be inferred from an earlier wake.

Persist immutable IDs/canonical bytes before sending. Crash after remote acceptance but before local acknowledgment must recover the same event, not create a new offer. Re-envelope only according to an explicitly verified transport contract; task event identity makes retransmitted identical content idempotent, but cannot replace FS ratchet safety or **VHL replay association with envelope IDs**. Exact-envelope retry must preserve its originally approved recipient, content, envelope ID and attestation under existing replay semantics. Distinguish the attestation’s signed action/content binding from the replay set’s envelope-ID association; this does not claim the envelope ID is a signed attestation field. Creating a fresh envelope requires a fresh valid attestation for the current exact approved action/recipient, with replay verification recorded against the new envelope ID under the current VHL mode; never copy a Tier 2 attestation or replay an already-consumed approval onto a new envelope. If this requires human approval, keep the send blocked until obtained. Task-level duplicate detection cannot authorize a transport-level VHL replay. Test successful and uncertain-acceptance retries independently at both layers. Reuse the reviewed outbox mechanism from Packet E where possible through an integrator-owned adapter.

Retain minimal replay, cancellation, terminal and equivocation tombstones beyond content retention for the entire supported replay horizon. No TTL-driven purge of active-task safety records. A restored backup or copied state cannot reauthorize execution: pause accepted/claimed tasks for reconciliation and rebuild authenticated history; never restore approvals or active claims as live. If bounds, history or replay guarantees cannot be satisfied, fail closed and surface recovery required. Bound global and per-peer live tasks, orphan stop markers, predecessor gaps, total ledger/outbox bytes and events per task. Reserve capacity for stop/terminal/recovery evidence for already-admitted work, separate from untrusted orphan/admission quotas; a peer flooding orphan cancels must not prevent recording a real task’s cancellation. Reject or quarantine new admissions before exhausting that reserve. On storage failure, stop new effects/admission and report recovery required; never delete a safety marker merely to resume progress. Exact retention and numeric limits need owner approval, not invented defaults.

## Accepted requirement, invariants and proposed choices

- **D7 accepted product requirement:** agents must be able to assign work directly to existing agents on their team/crew. This is supplied by the user’s new Courier requirement, not a request for another generic permission gate. This scoped handoff extension satisfies that intent while keeping the retired shared notes/boards/workflow subsystem out of Courier.
- **D8 proposed interface and limits:** use the CLI and schema in this document and the concrete validation candidates below. These are engineering proposals, not user-approved permanent defaults. H must settle canonical fields and support-proof freshness/binding before dependent code; I must verify durability/replay and benchmark limits before release.
- **D9 safety invariant:** explicit recipient admission and reply policy; local approvals bind the offer hash. Transport VHL and execution authorization remain separate. Team membership never implicitly grants privilege. Implement and test this invariant rather than asking the user to waive it.
- **D10 proposed bounded topology:** one shared locked ledger per executing principal, one attempt, no automatic takeover. Independent devices using copied principals are unsupported until a separate shared claim/fencing service is designed. This is a disclosed implementation proposal, not a claim the user approved a distributed-execution limitation.

### Concrete candidates to validate

Use these as initial test/benchmark inputs, not silent permanent defaults: 16 KiB canonical task-event payload; 100 live tasks per context and 16 per peer; 1,024 events per task; 128 MiB total ledger/outbox storage including a dedicated 16 MiB stop/terminal/recovery reserve; 128 predecessor-gap events globally and 16 per peer; 256 orphan stop markers globally and 16 per peer. Reject new admission before exceeding its budget; never consume the safety reserve for ordinary new offers.

Proposed timing: acceptance window at most 24 hours, execution deadline at most seven days after offer, a 60-second local claim lease renewed every 20 seconds, a 60-second clock-skew tolerance, and startup plus five-second local reconciliation polling. Lease expiry never triggers takeover. Proposed support evidence must be authenticated for the exact principal/origin/version and no older than five minutes; **this is not a claim that the current directory supports such a proof**. If its signed material cannot meet the bound, design and review a narrow support proof before H/I exposes sending.

Proposed content retention is 30 days after a terminal outcome, with minimal terminal/cancel/replay identity tombstones retained without time-based deletion in v1, within the total safety budget. When that budget cannot retain the necessary history, stop new admission and require forward recovery; do not evict safety evidence to keep accepting tasks. Numeric tuning and the supportable replay horizon require explicit transport-retention, clock, restart, compaction and malicious-replay tests before release. A 30-day content policy is not a 30-day execution-replay guarantee.

### Independent design review outcome

Independent review approved the proposal as design-only after correcting durable wake recovery, cancel-before-offer handling, acyclic offer hashing, pre-admission/accepted-waiting states, old-client compatibility limits, VHL action-versus-envelope replay semantics, reserved stop capacity and packet ownership. That outcome does not establish runtime correctness or approve policy, implementation readiness, merge or rollout. Remaining engineering choices include the exact support proof, measured limits and supported replay horizon, runtime adapter/CLI contract, and the proposed single-ledger topology.

## Acceptance gates

- Crash after durable offer commit but before wake delivery is recovered by startup/poll reconciliation; duplicate wake and poll paths cannot create duplicate claims. Pre-accept human waiting remains non-executable through restart; accepted waiting is distinguishable from running and makes no availability guarantee.
- Offer-hash golden vectors prove the acyclic core/event preimages and bind every instruction, party, deadline and team-provenance field.
- Cancellation at actor sequence 2 before missing offer sequence 1 installs only the exact-tuple deny marker; withheld predecessors, quota exhaustion and replay never unlock execution. Invalid sender/tuple cannot stop another party’s task.
- Exact-envelope retry preserves the original VHL action binding and envelope-ID replay association; a fresh envelope cannot reuse old Tier 2 attestation/consumed approval even when task IDs match.
- A addresses existing B as `b@crew`; B receives structured offer without spawning. Authenticated consent leads to one claim and a returned result. Decline and blocked-for-human are visible and do not execute.
- Team membership/ownership, malicious task prose, claimed approval, changed alias, another team member or forged nested identity cannot authorize acceptance, tool access, completion or cancellation.
- Sender's scoped VHL approval cannot be reused for another peer or changed content; recipient policy independently denies execution; FS-required tasks cannot downgrade through protocol-DM handling.
- Retired `cs:1,t:state` frames remain retired, including future version numbers. On conforming clients, disabled/unsupported/unknown-version/malformed recognized task frames cause no execution or plaintext fallback. Older-client fixtures demonstrate raw-chat rendering; missing/stale/withdrawn or known-incompatible authenticated support must prevent the sender from transmitting task content. An unobservable software downgrade cannot be detected or prevented by this gate. Existing group/contact/receipt/VHL paths remain unchanged.
- Wrong offer hash/origin/recipient, duplicate JSON keys, unknown fields, invalid suite, overflowing sequence, event fork, missing predecessor and oversize bounds fail safely.
- Duplicate offers across inbox/dashboard/re-enveloping and crashes around outbox/cursor/admission/claim/result commits produce one ledger event and no duplicate claim. Test full cross-process race, not only goroutines.
- Two local claimants yield one winner; stale fence cannot publish or act through compliant adapter. Lease loss/restart/backup restore never automatically restarts work. Demonstrate and document inability to fence an unrelated external process that ignores the adapter.
- Cancel-before-offer, cancel-before-accept, cancel-before-claim, cancel-during-side-effect and completion/cancel races preserve evidence and honest state. Expired/removed roster does not strand the authorized stop path.
- Clock rollback and acceptance/deadline expiry stop new admission/effects without claiming remote inactivity. Withheld response remains unknown; delayed authentic terminal result is retained as evidence.
- Only explicitly authorized result recipients receive data. Team owner/other members and relay cannot read task content. Links are not automatically fetched; no plaintext dashboard push.
- Orphan/gap/task floods hit explicit global/per-peer quotas without consuming the reserved capacity needed to stop already-admitted work. Disk-full paths block new effects and never evict live safety evidence.
- Pre-claim decline/expiry/cancellation are valid assignee-ledger control outcomes without a fabricated lease; they cannot masquerade as execution results.
- Terminal/replay records survive content compaction and supported retention. Backup recovery cannot resurrect task authority. Main and named contexts cannot collide.
